# Suite implementation profile

The application accepts JSON scenario objects with five top-level domains. The schema defines their types and required values; runtime validation also checks references and graph semantics.

The field tables below are generated from the same schema used by Builder, AI authoring, and server validation.

# Packages and role outputs

Builder includes output tools. A published scenario can produce a facilitator guide, learner brief, event map, or operational checklist without becoming a new product. Every generated view should identify the scenario revision it describes.

The application JSON export wraps scenario content with format/version and revision identity, timestamp, and digest. That envelope is a Suite package, not a normative definition of the .usim standard. JSON schema validates structure; a digest identifies serialized content; neither establishes clinical correctness or ownership.

Marketplace listings and import receipts, Center deliveries and readiness, Campus runs and reflections, and Builder graph layout are product records. They remain outside exported scenario content. Classroom remains part of Campus; output tools remain part of Builder.

# Validation and interoperability

Scenario imports are validated against the application schema. Unknown fields, invalid references, unsupported values, and mismatched content digests produce validation errors.

Preserve explicit units and authored values. Do not guess missing data or execute arbitrary script content.

# Suite parameter guide

This guide describes the current Scenario type. The profile-schema download defines structural requiredness and the validator applies additional constraints. Optional means a value may be omitted; it does not mean normal, negative, or zero. Arrays contain separate items; text records map an authored heading to a finding.

metadata.title (string): a concise case title that distinguishes it in a library. metadata.description (string): the premise, scope, and intended activity; include what makes the scenario useful without relying on the title alone. metadata.author (string): attribution as one display string, not an account identifier or a structured contributor list.

metadata.diagnosis (optional string): the authored diagnostic or subject-matter focus, such as “Communication rehearsal.” metadata.specialty (optional string): the intended discipline. metadata.level (optional string): expected learner stage; explain assumed capability in prerequisites instead of relying solely on “Intermediate.” These strings are descriptive metadata, not enforced taxonomies or access controls.

metadata.durationMinutes (optional number): planned scenario duration in minutes, accepted from 1 through 1440. It neither starts a timer nor ends a run. Put setup and debrief expectations in preparation or education text; no separate structured setup/debrief duration exists in this profile.

patients (object): one patient profile despite the plural name. patients.name (string) is the fictional display name. patients.context (string) explains why the patient is here and the immediate situation. Multiple simultaneous patients require a future schema and runtime change; do not place an array here.

patients.demographics.age (optional number): authored age; use years consistently in current content and state finer infant age in the narrative when needed, because this field has no age-unit discriminator. gender (optional string): the person's authored gender description. weightKg and heightCm (optional numbers): weight in kilograms and height in centimeters. These values do not automatically calculate dosing or other physiology.

patients.history.chiefComplaint (optional string): the presenting concern in the patient's or referring team's words. presentIllness (optional string): onset, sequence, progression, relevant associated findings, and interventions before arrival. Keep the timeline consistent with the baseline state and available results.

patients.history.medical and surgical (optional string arrays): separate relevant conditions and prior procedures, with timing or consequences when useful. medications (optional string array): background medication history, including an authored dose, route, frequency, or last use in text when relevant; this is not an executable medication order. allergies (optional array, maximum 64 entries): { substance: string, reaction?: string, severity?: mild | moderate | severe | unknown }. Each text field permits up to 1,000 characters. Severity describes the authored reaction, not predicted future risk; omitted means unspecified and unknown is explicit. Text entries are also accepted, including unknown or no-known-allergy statements. Never infer reaction or severity from free text. An empty list does not establish that allergies were checked.

patients.history.family and social (optional strings): relevant family context, living situation, supports, exposures, and functional context. patients.history.ros (optional string record): system name to authored symptom findings, for example general → “No additional symptoms reported when asked.” Record explicit negatives only when authored; omission has no clinical meaning. For a wholly unobtainable ROS, use a single key “Unable to obtain” with an explicit reason statement (usim:unavailable-ros@1.0.0); do not combine this status with normal system defaults or infer it from the diagnosis.

patients.examination (optional string record): examination heading to observable finding. Include method or access conditions when relevant, such as a finding revealed only on a focused examination. These strings describe content; they do not create examination-triggered events. Use actions and states to model an explicit decision path.

patients.vitals (optional object): initial authored numeric measurements. hr is heart rate in beats/minute; sbp and dbp are systolic and diastolic pressure in mmHg; rr is breaths/minute; spo2 is percent from 0 to 100; temperature follows the current example's Celsius convention; etco2 follows its mmHg convention. The current payload has no unit field or conversion mechanism, so do not mix temperature or gas-pressure conventions. These are measurement labels, not target ranges.

Vital value validation: all supplied numbers must be finite and nonnegative; spo2 is capped at 100 and the other measurements at 1000. These broad software limits are not physiologic reference intervals. Missing measurements remain unspecified at initialization. Later partial overrides retain prior measurements; zero is a supplied value and never a missing-data marker.

environment.setting (string): clinical or learning location and the circumstances in that location. requirements (string array): tasks the simulation center must complete before the session, one concrete action and setup outcome per entry (for example, program initial manikin vitals, stage result cards for timed release, or brief actors). Do not list equipment here or disguise inventory items with "Ensure available" or "Prepare". equipment (optional string array): named equipment, supplies, manikins, documents, and other resources with relevant configuration or substitutions. These are portable content requirements, not Center inventory counts or room bookings.

environment.actors (optional array): each actor has id, name, role, and brief strings. Optional demographics contains age (years, 0–150) and gender; voice mode uses these authored values for voice selection and delivery, with a neutral adult fallback. No demographics are inferred from names or occupations. id distinguishes the actor; name is the displayed person or character; role describes the simulation responsibility; brief contains opening behavior, information boundaries, cues, and responses. An actor does not become a logged-in facilitator or an automated agent merely by being listed.

education.objectives (array): observable learning outcomes, each either text or { id, statement, acgmeCompetencies? }. Structured objectives have stable IDs and optional unique ACGME core competency codes PC, MK, PBLI, ICS, PROF, SBP. education.assessment[].objectiveId optionally links an action-based assessment criterion to a structured objective. Mappings do not establish Milestone levels or competence. debrief (string): prompts connecting observations and decisions to the objectives. audience (optional string): who the exercise is for. prerequisites (optional Markdown string): formatted instructions and module links for knowledge, technical skills, or preparation assumed. prerequisiteDocuments (optional array): uploaded preparation files with id, name, and dataUrl; use the upload control, never invent document bytes. Learners can download these before starting; completion is not tracked. rationale (optional string): why this scenario and its decisions address the learning need.

Baseline authoring: baseline is exclusively the starting conditions. Newly authored actions and resource advanceToStateId destinations must not return to baseline, including baseline self-loops. A meaningful milestone such as reviewing critical findings leads to a distinct triggered phase such as Critical findings recognized, even if physiology is unchanged. Routine resource requests need neither graph actions nor extra states. Preserve existing or explicitly imported baseline loops during unrelated edits; this authoring rule does not invalidate saved files or change runtime behavior.

When separating recognition from baseline, keep deterioration scheduled from its original source and original deadline: entering the recognized phase does not cancel or restart the timer. Recognition is not effective treatment. Only appropriate treatment actions cancel deterioration, and cancelOnActionIds must cover those actions on every relevant branch. Preserve assessment action IDs and references when revising the graph.

events.states (array): the scenario's phases. Each id is a stable reference used by actions; title is the human-facing name and can change independently. kind is baseline, triggered, scheduled, or conclusion. Author exactly one baseline and at least one conclusion. A scheduled kind alone does not schedule anything: an incoming action with trigger scheduled supplies the timer.

patients.monitor and state.monitor optionally select a schematic monitor rhythm using a canonical rhythm identifier; pulsePresent is a separate boolean. An explicit state rhythm replaces the preceding rhythm/pulse configuration; a connection-only event preserves it. State monitor connections patch only supplied channels and persist until changed. Never infer current rhythm solely from the diagnosis or heart rate. See docs/monitor-rhythms.md.

State learnerNote (string): the prompt or information intended for the learner at this phase. tutorNote (string): expected behavior, facilitation instructions, cues, and the reason for the transition. key (optional boolean): marks an educationally important phase; it is not a passing score or a guarantee that all paths visit it. vitals (optional vital object): values overlaid when entering the state, retaining other measurements.

events.actions (array): directed transitions. id identifies the edge; label describes the choice or timed event; from and to reference existing state IDs. Separate edges represent the same decision in different source states. Labels use 2–6 words, at most 48 characters, describing observable actions or timed events. Put conditions and what happens in the optional description string (up to 6000 characters). Do not append destination titles.

Action trigger (optional enum action or scheduled): omitted represents a learner activity completed by AI interpretation, optional direct resource recognition, or explicit learner/facilitator confirmation. completionCriteria supplies the AI criterion; omitted criteria fall back to the label and description. delaySeconds (optional number): for a scheduled edge, a strictly positive delay of at most 86400 simulated seconds measured from source-state entry. A delay on a manual edge does not postpone the click. Each scheduled edge starts once on the first occurrence of its source event and remains pending across later events. Multiple outgoing timers run independently; re-entry does not restart them. Explicit cancellation or conclusion stops pending timers.

Action labels name learner activities. Suite completionCriteria is an optional plain-language criterion evaluated by the AI against learner intent, conversation, and simulator interactions; equivalent wording is accepted. If omitted, the label and description provide the criterion. The AI returns evidence-backed executions separately from ambiguous choices. Multiple explicit orders can be recorded in one atomic batch before evaluating authored transitions. Only currently available actions qualify, including selected timer-canceling actions whose source events have occurred; stale interpretations and competing state transitions are rejected. Fulfilled actions that converge on the same destination without transition effects may be recorded together; the destination is entered once. The AI cannot invent states or patient effects. Explicit facilitator confirmation remains available. Optional completion { mode: any | all, objectIds: Resource ID[] } adds direct resource recognition; automatic state releases do not count. Request completion remains distinct from delayed result availability.

Suite scheduled transitions may declare cancelOnActionIds: Action ID[]. Completion of any referenced learner action prevents the scheduled transition for the rest of that run, including after re-entry; self-loop actions can cancel deterioration without changing the current state or restarting its timer. Cancellation never reverses an event that already fired. While a timer is pending, selected unfinished actions remain available after their source event has occurred, even if another event is current. Future-source actions stay unavailable; completion still follows the selected action's destination, and a self-loop stays in the current event. Conclusion states do not allow this recovery. Scheduled delays are relative to the first occurrence of the source event and remain pending after other events occur. Each scheduled edge fires at most once per run. At a deadline, commands are processed in order: a completion saved before clock advancement cancels the pending transition; advancing the clock to the deadline first fires it.

Suite facilitator confirmation requests every selected resource for an all-resource action if not already requested. For any-resource actions, confirmation records the observed activity without guessing which alternative was used; record the specific resource separately when results are needed. Automatic recognition does not request unchosen alternatives. Builder authors resource links only in the state inspector under Results → Configure resources, using releaseOnStateId to reveal a resource on state entry. Transitions expose no linked-resource picker or resource configuration sheet; Edit destination state opens the owning state inspector. action.objectId requests a resource during a transition. state.resourceTrigger enters a state when its requested results are available.

Action objectId (optional string): requests the resource during the transition if not already used. Builder authors resource links in the state inspector under Results → Configure resources. effects (optional vital object): absolute vital values applied during the transition. Builder authors scenario-specific patient changes on destination state vitals. For an immediate object-linked transition, object effects apply first, action effects second, and destination-state values last. Avoid overlapping values unless that precedence is intentional.

State resourceTrigger (optional { mode: any | all, objectIds: string[] }): enters the state once when any or all selected learner-requested resources have available results, after their response delays. A request alone does not satisfy a delayed result. Incoming transitions remain alternative paths. For labs-resulted events, select the labs here rather than creating a transition that enters the state immediately when ordering them.

events.objects (optional array): reusable resources. id identifies the resource; type is medication, diagnostic, procedure, equipment, consultation, or information. Diagnostic resources require diagnosticCategory: lab, imaging, or physiologic; other types must omit it. Procedures include actions performed on the patient by nursing, physicians, or other clinicians. Equipment identifies the device, not its insertion or application. name is the label; description supplies context and purpose. Classification does not activate a type-specific physiology engine.

Object labResults (optional array of name/value/unit strings) preserves editable laboratory values including decimals and qualitative results. image (optional dataUrl/description object) embeds a validated PNG, JPEG, or WebP, at most 12 MiB of data URL characters. releaseOnStateId (optional state ID) releases once on entry to that event after delaySeconds, blocking early manual requests; this takes precedence over action objectId requests. Deleting the state unlinks the release. advanceToStateId enters an existing event when the response is released; this excludes resource vital effects. effectPercent applies signed percentages to current values at response time and excludes absolute effects. Lab values precede result notes in learner output.

Object result (optional string): learner-facing information returned on use; blank or omitted result falls back to description. delaySeconds (optional number): time from request until availability, from 0 through 86400 simulated seconds; omitted means immediate. source (optional string): provenance or source citation text, not a bundled asset, authenticated URL, or clinical verification flag.

Object effects (optional vital object): absolute values applied when the result becomes available, immediately for a zero delay. The object can be requested directly by the runtime or through an action reference; each object is used once per run. A later action linked to an already-used object still transitions but does not request it again. Repeated dose or serial-result behavior needs distinct objects.

Timing collisions: delayed result effects due at a scheduled transition's instant apply before the transition's action and destination values. All equally due scheduled edges fire in action array order, unless an earlier event ends the scenario. Later events overwrite only the vital values they specify. A delayed result can arrive after leaving the state that requested it. Conclusion stops further clock advancement, so do not rely on a later result for essential closure.

Scenario content excludes graph positions, publication revision identity, scheduled delivery dates, learner identities, and run observations. Use the Suite package envelope for import/export; the downloadable scenario example is the inner content only. New clinical variables, media manifests, conditional rules, or assessment structures require explicit profile support rather than extra undocumented JSON keys.
